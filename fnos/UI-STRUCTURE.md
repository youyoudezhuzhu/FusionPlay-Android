# FusionPlay fnOS 管理界面：现状结构与重规划输入

> 用途：把当前前端的信息架构、页面内容、组件、接口依赖和约束完整描述出来，
> 交给设计/模型做 UI 重规划。**本文只描述现状，不含重规划结论。**
> 对应代码：`fnos/frontend/index.html`、`app.js`、`style.css`（纯静态，无构建步骤）。
> 后端 API 契约见 `fnos/ARCHITECTURE.md` §3.1 与 `fnos/backend/src/http.rs`。

---

## 0. 一句话概括

一个**中文、深色、桌面优先**的 NAS 应用管理面板：5 个页面（概览 / 接收协议 / 音频输出 /
音频校准 / 设置·诊断），全部数据来自本机 Rust 服务的 JSON API；无框架、无第三方依赖、
hash 路由、2 秒轮询、每页有"未保存草稿"机制。

---

## 1. 运行环境与不可变约束

| 约束 | 说明 |
|---|---|
| 宿主 | 飞牛 fnOS「应用中心」内嵌 iframe，通过统一网关访问 |
| URL | 生产：`/app/fusionplay-fnos/`；开发：根路径 `/`。前端必须自动识别 gateway 前缀（当前用 `location.pathname` 推导 `GATEWAY_BASE`） |
| 技术 | 纯 HTML/CSS/原生 JS（IIFE，无框架、无 npm、无 CDN、无外链字体） |
| 语言 | 中文优先；代码注释英文 |
| 主题 | 当前**仅深色**（GitHub Dark 风格配色） |
| 数据真实性 | 后端无数据时显示「—/未上报/加载中」，**禁止演示数据、假进度、假同步状态** |
| 后端接口 | 前端可整体重写，但下列 API 与字段是后端已实现的契约，重规划时**不能要求后端改协议**（可以增字段，但不能假设已有 SSE/WebSocket/鉴权） |
| 轮询 | `GET /api/status` + `GET /api/config` 每 2s；日志 4s、诊断 10s；页面隐藏时暂停 |

**当前没有任何登录/鉴权/多用户概念**（依赖 fnOS 网关的访问控制）。

## 3. 信息架构（5 页）

| # | 页面 | hash | 主要任务 | 数据源 |
|---|---|---|---|---|
| 1 | 概览 | `#/overview` | 一眼看健康状态/当前播放/输出设备/错误 | `/api/status`、`/api/logs` |
| 2 | 接收协议 | `#/protocols` | 三协议开关、广播名、网卡，保存后宿主重启 | `/api/config`、`/api/status`、`/api/diagnostics` |
| 3 | 音频输出 | `#/output` | 发现/多选声卡、响度/延迟/采样率、测试音 | `/api/devices`、`/api/config`、`/api/devices/refresh`、`/api/devices/test` |
| 4 | 音频校准 | `#/calibration` | 全局衰减、音量曲线（含图形编辑）、每设备 dB/延迟 | `/api/config`、`/api/calibration`、`/api/calibration/preview` |
| 5 | 设置 / 诊断 | `#/settings` | 版本/运行统计、日志与级别、配置导入导出、ALSA/网卡诊断 | `/api/status`、`/api/logs`、`/api/logs/level`、`/api/export`、`/api/import`、`/api/diagnostics` |

页面进入时按需拉取：概览/设置 → 日志；协议/设置 → 诊断；输出 → 设备列表；校准 → 曲线预览。

## 4. 页面详述

### 4.1 概览（Overview）

自上而下 / 三列卡片流：

```
┌ 协议状态卡 ×3 ─────────────┐ ┌ 当前媒体 ────────────────┐
│ AirPlay 2   [运行中]        │ │ 封面图（无则隐藏）        │
│ 名称/端口/客户端/详情       │ │ 当前音源 / 标题/艺术家/专辑│
├────────────────────────────┤ │ 播放进度 / 音频格式       │
│ DLNA (DMR)   [监听中]      │ │ 引擎采样率 / 设备采样率   │
├────────────────────────────┤ └───────────────────────────┘
│ 小米妙播     [运行中]      │ ┌ 发送端逻辑音量（只读）────┐
└────────────────────────────┘ │ AirPlay 2: −12.0 dB (25%) │
┌ 输出设备 ───────────────────┐ │ DLNA: 60%                 │
│ 设备 | 在线 | 状态 | 缓冲 |  │ │ 小米妙播: 45%             │
│ 漂移 | underrun             │ └───────────────────────────┘
└─────────────────────────────┘
┌ 错误与最近事件 ─────────────────────────────────────────────┐
│ 错误列表（红）或「暂无错误」                                  │
│ <pre> 最近日志/事件（来自 /api/logs，最多 200 行）   [刷新事件] │
└─────────────────────────────────────────────────────────────┘
```

要点：
- 协议卡数据来自 `status.protocols.{airplay,dlna,miplay}`：`enabled/state/detail/clients/port`；
  state 有中英映射（running/listening/playing/streaming/paused/…→中文）。
- 媒体卡数据来自 `status.media`：`title/artist/album/cover_url/position_ms/duration_ms/detail_codec`；
  `detail_codec` 是原始格式描述（如 `pcm_s16le · 44.1 kHz · 2 声道 → 48 kHz stereo`）。
- 发送端音量是**只读**的（明确产品要求：发送端是主音量，NAS 只做校准）。
- 设备表来自 `status.devices`（`DeviceStatus`）。
- 事件区是日志尾部，非真实事件时间线（后端没有 SSE）。

### 4.2 接收协议（Protocols）

```
┌ 协议卡 ×3（grid）─────────────────────────────────────────────┐
│ AirPlay 2                [运行中]                             │
│ [x] 开启接收                                                  │
│ 广播名称（写入 config.receiver.name） [____________________]  │
│ 网络接口（留空 = 自动）  [自动 / eth0 / … ▾]                  │
│ 端口 5000 | 发现状态 监听中 | 客户端 0 | 详情 …               │
└──────────────────────────────────────────────────────────────┘
┌ 保存区 ───────────────────────────────────────────────────────┐
│ [有未保存修改]   [保存协议设置 (primary)] [撤销未保存修改]     │
│ 错误提示（红）                                                │
└──────────────────────────────────────────────────────────────┘
```

- 三张卡共享同一个 `config.receiver.name` / `config.receiver.interface`（改任意一处三卡同步），
  每卡独立 `protocols.{key}.enabled`。
- 保存 = `PUT /api/config`；后端**自动重启协议宿主**使开关/名称/网卡生效。
- 前端会区分「保存成功且已生效」「已落盘但宿主重启失败」两种提示（比较返回的 config 与实际 GET）。
- 网卡下拉来自 `/api/diagnostics.interfaces`（后端枚举 `/sys/class/net`，排除 lo）。
- MiPlay 端口后端目前上报 0 → UI 显示「—」，不猜测。

### 4.3 音频输出（Output）

```
┌ 页头 + [有未保存修改] [刷新设备] [撤销修改] [保存并应用] ┐
│ 设备消失横幅（黄色）：N 个已配置设备当前不可见            │
├──────────────────────────────────────────────────────────┤
│ 启用 | 设备 | 稳定 ID | 在线 | 采样率 | 通道 | 默认格式 |  │
│ 响度(slider −30~0dB) | 延迟(0–2000ms) | 缓冲 | 漂移 |      │
│ underrun | 操作(测试音/移除)                               │
└──────────────────────────────────────────────────────────┘
提示：响度范围/延迟范围/默认格式语义/保存流程说明（PUT config → refresh）
```

- 13 列表格，`min-width: 960px`，外层横向滚动（移动端体验差，是当前主要痛点之一）。
- 设备来源：`/api/devices`（ALSA 实测）+ `config.audio.devices`（已保存配置）合并；
  已配置但当前不可见的设备保留行并标红/横幅提示，可「移除」。
- 每设备字段：`enabled`、`sample_rate`（0=跟随设备）、`gain_db`（−30~0）、`delay_ms`（0–2000）。
- 「测试音」→ `POST /api/devices/test {id}`，播放 1s 正弦（后端实现）。
- 「保存并应用」= `PUT /api/config` → `POST /api/devices/refresh`；保存失败会回读确认是否已落盘。
- 在线设备显示实测采样率列表/通道/默认格式（来自 `DeviceInfo`）；运行态显示 `buffer_ms/drift_ppm/underruns`。

### 4.4 音频校准（Calibration）

```
┌ 全局校准卡 ──────────────────────────────────────────────┐
│ 全局输出衰减  [=========○===] 100%（0–100，默认100）      │
│ [ ] 静音输出                                             │
│ 音量曲线 [线性/柔和/均衡(默认)/自定义 ▾]                  │
│ [保存并应用] [恢复默认]     状态badge                    │
└──────────────────────────────────────────────────────────┘
┌ 自定义曲线编辑器卡 ──────────────────────────────────────┐
│ [添加控制点] [删除选中点] [重置曲线]  选中「自定义」后可拖动│
│ ┌─────────────────────────────── canvas 640×260 ───────┐ │
│ │  y: 输出 (0-100%)  折线 + 控制点（首尾固定 0/0 与 1/1）│ │
│ │  x: 发送端逻辑音量 (0-100%)                            │ │
│ └───────────────────────────────────────────────────────┘ │
│ 控制点：0%,0% → 25%,15% → … → 100%,100%（首尾固定）       │
│ 说明：拖动实时 POST /api/calibration/preview；x/y 单调不减  │
└──────────────────────────────────────────────────────────┘
┌ 每设备响度/延迟表 ───────────────────────────────────────┐
│ 设备 | 稳定 ID | 启用 | 响度 dB | 延迟 ms                  │
│ （无设备时提示先去「音频输出」选择）                       │
└──────────────────────────────────────────────────────────┘
```

- 全局参数：`audio.global_attenuation_percent`（0–100）、`audio.muted`、
  `audio.curve.kind`（linear/soft/balanced/custom）、`audio.curve.points`（0–1 的 `[x,y]` 数组）。
- 曲线编辑器交互：拖点（x/y 单调 clamp）、双击空白增点、方向键微调、Delete 删除、
  首尾固定不可删、添加/删除/重置按钮、去抖预览、保存（`PUT /api/calibration`）。
- **明确标注**：这些参数不是发送端主音量；后端不支持每设备曲线覆盖（只有全局曲线 + 每设备 dB/延迟），
  UI 不伪造该能力。
- 每设备表与「音频输出」页字段重叠，但此处只改 dB/延迟/启用。

### 4.5 设置 / 诊断（Settings）

```
┌ 运行状态卡：版本 / 运行时长 / 音频后端 / 协议宿主 / 日志文件 / 构建信息 ┐
├ 运行统计卡：当前音源 / 主混音帧数 / 丢弃帧数 / 输出设备 / 累计underrun / 日志级别 ┤
├ 日志卡：级别选择 [error/warn/info/debug/trace] [应用级别] [自动刷新] [刷新]   │
│        <pre> 最近 200 行日志（等宽、滚动、可聚焦）                          │
├ 配置卡：[导出配置 JSON 下载] [导入配置(选择文件)] + 当前配置摘要(kv) + 错误提示 │
├ 诊断卡：音频后端 / 日志文件路径 / 网卡 chips / /proc/asound cards <pre> / pcm <pre> │
└─────────────────────────────────────────────────────────────────────────┘
```

- 日志级别切换 → `POST /api/logs/level`（后端运行时生效，无需重启）。
- 导出 → `GET /api/export` 的 JSON 下载；导入 → 文件选择 + `POST /api/import`（≤1 MiB，失败提示）。
- 诊断只读；ALSA 原始 `/proc/asound/cards`、`pcm` 文本便于排障。
- 构建信息来自二进制版本；无 git hash 就不显示，不猜测。

## 7. 关键交互与状态

1. **轮询与降载**：2s `/api/status`+`/api/config`；页面 `hidden` 时停止；`tickBusy` 防重入；
   `立即刷新` 手动触发。无 SSE/WebSocket。
2. **草稿机制（三页）**：协议/输出/校准各自维护 draft；轮询只更新非草稿字段，避免覆盖未保存编辑；
   有改动显示脏标记；保存成功清脏；撤销恢复上一次配置。
3. **保存流程**：
   - 协议：`PUT /api/config` → 后端重启宿主（1–3s），前端回读确认，失败区分"已落盘/未生效"。
   - 输出：`PUT /api/config` → `POST /api/devices/refresh`。
   - 校准：`PUT /api/calibration`；曲线预览走独立接口。
   - 导入：`POST /api/import` → 可能重启宿主 → 刷新状态。
4. **空/错状态**：加载中「加载中…」；无数据「—/未上报/暂无错误」；断线顶部 banner + toast；
   表单校验（响度 −30~0、延迟 0–2000、曲线单调、名称 ≤64）在前端 clamp + 后端校验双保险。
5. **可访问性**：部分 aria-label/aria-current/aria-live、键盘可操作曲线点、`prefers-reduced-motion`。
   （不完整，重规划可系统化。）

## 9. 当前已知问题 / 重规划时值得解决的痛点

1. **输出设备 13 列表格**：桌面尚可，移动端必须横向滚动；信息密度过高，缺"按设备分组/详情抽屉"。
2. **信息层级平铺**：概览三协议卡 + 媒体 + 音量 + 设备 + 错误，缺少"健康度/待处理问题"聚合。
3. **没有实时事件流**：只有 2s 轮询 + 日志尾部；播放/接管/错误变化不够"即时"。
4. **协议保存会重启宿主**（1–3s 中断），UI 只有文字提示，没有进度/恢复反馈。
5. **曲线编辑器**：功能完整但样式基础、缺网格刻度/数值输入/预设管理（后端也只支持全局曲线）。
6. **无每设备曲线覆盖**（后端不支持），重规划不应设计此交互或需先加后端。
7. **日志区**：无过滤/关键字搜索/级别着色/下载；诊断信息不可一键复制。
8. **无登录/多用户/权限**；无"操作审计"。
9. **无亮色主题/无 i18n**（当前中文硬编码在 HTML/JS）。
10. **无空状态插画/引导**：首次使用（无设备、无配置）时页面较空。
11. **无设备拓扑/多设备同步可视化**：只有表格数值，缺"多设备是否同步/延迟差异"的直观表达。
12. **错误展示分散**：banner/toast/`errors` 区/表单错误四处，缺统一问题中心。
13. **构建信息无 git hash**（后端只给 version），设置页无法展示更完整构建元数据。
14. **无移动端导航模式**：5 个 tab 在窄屏横向挤压（当前仅缩小 padding）。

## 10. 给重规划者的硬性要求（做新 UI 时必须保留）

1. 5 类功能不可丢：概览/协议开关+名称+网卡/多设备输出/校准（全局+曲线+每设备）/设置诊断（日志+导入导出+诊断）。
2. 所有数据必须来自上述 API，不允许演示数据/假进度/假同步；空状态要明确。
3. 必须处理 fnOS gateway 前缀（`/app/fusionplay-fnos/`）与根路径两种部署；静态资源相对路径可用。
4. 不能引入需要联网的 CDN/字体/图标服务；构建产物必须能直接由后端静态目录提供（无 npm 构建也可接受）。
5. 协议保存会触发宿主重启，UI 必须如实提示（不能假装"立即生效"）。
6. 发送端音量只读；NAS 端只做校准（全局衰减/曲线/每设备 dB/延迟/静音）。
7. 中文优先；深色或亮暗双主题均可，但要与 fnOS 应用风格协调、响应式（桌面 + 手机）。
8. 保留"未保存草稿/撤销"能力，避免轮询覆盖用户编辑。
9. 前端整体可替换，但**不得要求改后端 API 契约**；如需新增接口，请单独列出（后端可加）。
10. 所有"待真机验证"的能力（AirPlay 实际投放/DLNA 控制端/MiPlay/多声卡听感）不得在 UI 里表现为"已验证"。
